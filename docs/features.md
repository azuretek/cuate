# Features

What works today, and the test that proves each. Planned work is at the end.

## The server

- Chats, newest first, each with a preview of its last message: `server/test/api.test.js`, "chats list newest first".
- The chat list and its previews held in memory from the start and kept current by live messages, so a chat list never waits on the engine: "the chat list and its previews are held from the start", "a live message moves its chat to the top".
- A chat's history, paged from newest to oldest: "history pages from newest to oldest".
- Message search through the engine's own history, newest first, narrowed to one chat when asked: "search finds messages through the fixture engine".
- Settings kept on the server, so a value written by one device is read back by the next device token, and a change streams to every connected client: "a setting written by one device is read back by another", "a settings change is broadcast".
- Attachments by id, only from inside the Messages attachments folder: "attachments are served by id".
- Marking a conversation read, so a chat read on one device clears on every device: "opening a conversation marks it read".
- Sending text and files, off until switched on, rate limited, once per client key, with uncertain outcomes never retried: the send tests.
- Uploading a file from the device (`POST /api/v1/attachments`, the bytes as base64 in the one JSON shape HTTP and MCP share), held in the data folder's `uploads` only until it has been sent and swept after `uploads.keepHours`, capped at `uploads.maxBytes` from the spec and reported in `info` so a client can refuse a file before reading it: "a file from the device uploads...", "an upload is refused when...".
- Reacting to a message and replying to it in a thread (issue 138): a reaction goes out as one of the six standard tapbacks through the engine's bridge, added or taken off; any other emoji, or a reply or reaction while the bridge is down, is refused cleanly with its rate slot given back; both pass the sending switch and the rate limit, and a reply carries its parent to the engine: the reaction and reply cases in `server/test/send.test.js`, and "a reaction and a threaded reply go through the routes and the client..." in `server/test/api.test.js`.
- Live events over one WebSocket (new messages and tapbacks), resumed after a reconnect: "live messages stream", "tapbacks stream".
- Scoped tokens in the Authorization header only, stored hashed: "every other route needs a token", "a tooling token cannot send", `server/test/cli.test.js`.
- The engine restarted when it dies: "the engine is restarted when it dies".
- Declared, scrubbed log lines with no message text or tokens, even at debug: "no token or message text reaches a log line".
- `init`, `token`, `sending`, `doctor` and `run` on the command line: `server/test/cli.test.js`.

## The desktop app

- Connect with a server address and a device token, kept in the OS keychain: `desktop/test/bridge.test.js` and the desktop smoke.
- The chat list, a conversation with sender runs, time separators, photos, tapbacks and delivery state, and sending: the desktop smoke (`desktop/scripts/smoke.mjs`) and `core/test/rules.test.js`.
- The attach menu beside the emoji button: a short menu opening upward from the composer, a photo or video or any file staged above the field (or pasted), uploaded and sent with the text as its caption: the desktop smoke ("attach menu") and `core/test/rules.test.js`. Android opens the system picker for it from the shell's own chooser.
- A message's menu (issue 169), from a right click, a long click with the mouse or a long press with a finger: the message's time, then Reply in thread and React as icons from the shared set. Reply in thread is offered only on someone else's message, since a thread starts by answering another person. React opens the composer's own emoji panel, with its recents and search, and the emoji chosen there is the reaction; choosing your own reaction again takes it off, and a reaction the Mac cannot send is said under the message. Reactions float at the bubble's top outer corner (top right of a received message, top left of a sent one) with no background, and adding one moves no message (issue 182). Replies keep their place in time and carry a quiet dashed mark back to their thread, with no reply-to label; Reply in thread or the mark opens the thread as its own conversation, its first message and replies in order, above the rest of the conversation, which blurs behind it. Threads are one level deep, so a reply to a reply joins the same thread and a reply sent from the thread lands in it. The composer says "Replying in thread" with a cancel control and repeats none of the message; cancelling, Escape or sending brings the whole conversation back, and reduced motion drops the thread's arrival animation (issue 183): the desktop smoke ("react", "reply" and "phoneMessageMenu"), `core/test/message-actions.test.js` and `core/test/rules.test.js`.
- Live updates without a refresh, and OS notifications for incoming messages: the desktop smoke.
- A notice when an update is available and one when it is downloaded and ready, both through the same bridge notice path the new message notices use, each with its own switch the server holds: `core/test/rules.test.js`, "every notice type has its own switch...", and the desktop smoke, which fires a notice and then silences one.
- A notifications section in settings, one switch per notice type, written to the server so every client sees it: `core/test/rules.test.js`, "the settings page draws the schema...".
- Automatic download and install, off until its own setting is turned on: when it is on a found release is fetched with no further prompt and applied on quit, and when it is off nothing is fetched: `core/test/updates.test.js`, "the download preference narrows the platform answer, both ways".
- The download's progress, drawn as an in-app banner while it runs because a native notice cannot show a moving bar, with the artifact verified before the install by the check named per platform and a failure reported rather than swallowed: `core/test/updates.test.js`, "the verification check is named per platform...", `desktop/test/updates.test.js`.
- Installing from the banner inside the app: the banner that shows the download's progress carries the action that starts it and then offers the restart, and a failure says so rather than doing nothing; an explicit install is never blocked by the automatic-download setting. The bridge declares the two commands the page may call, `updates.download` and `updates.install`, and the page offers them only where the shell reports the build can install: `core/test/updates.test.js`, "the banner carries the action...", `desktop/test/updates.test.js`, `desktop/test/bridge.test.js`, and the desktop smoke, which asserts the banner's action calls the bridge command it says it does.
- Closing the window hides it to the tray (the menu bar on macOS, the notification area on Windows and Linux) and the app keeps running: the page's connection to the server stays open, notices keep firing, and a send in flight when the window closes still lands. The tray's menu carries Open, Settings, About, Check for updates and Quit; each raises the window first, restored if it was minimised, and opens its screen inside the app, and Check for updates runs the scheduled check and reports in the update banner, saying it is current or why the build cannot update itself. The tray's Quit, or a quit the platform asks for, is the only way the app ends: `desktop/test/tray.test.js`, `desktop/test/updates.test.js`, `core/test/updates.test.js`, the desktop smoke ("close to tray" and "tray"), and `desktop/scripts/prove-tray.mjs`, which captures the menu on each platform and the macOS template icon in the light and the dark menu bar.
- A theme the server holds, applied by every client without a rebuild, with light and dark both drawn from it and a skin that follows the system by default: `core/test/rules.test.js`, "a theme turns into custom properties for the scheme in force" and "a tweakcn theme is imported..."; the desktop smoke asserts the theme reaches the page in both schemes.
- A tweakcn theme converted into the token set, with every name it cannot carry refused and named: `core/test/rules.test.js`, "a tweakcn theme is imported, and every name it cannot carry is refused out loud".
- Importing a tweakcn theme from the settings page by pasting it: the pasted export is converted, added to the themes the server holds and put in force under `appearance.theme`, drawn by every client, the page says what it carried and names what it refused, an import that carries nothing is not stored, and Use default clears it: `core/test/rules.test.js`, "an import says what it carried...", `server/test/api.test.js`, "a theme is held on the server as one setting...", and the desktop smoke, which imports through the page, reads the theme back at the server and in what the page resolves, then clears it.
- Importing a theme by URL: the server fetches the URL itself (http or https only, bounded in time and size), reads tweakcn's registry JSON or the CSS export through the same converter the paste uses, adds it to the themes it holds under `appearance.themes` and answers with what it carried and what it refused; a bad URL, an answer that is not a theme, or a list already at its bound is refused with the reason and saves nothing. A value that could end its declaration or reach the network (`url()`, a semicolon, a brace) is refused rather than carried: `server/test/api.test.js`, "a theme given as a URL lands on the server..." and "a bad theme URL, or a URL that is not a theme, is refused...", `core/test/rules.test.js`, "a theme URL answer in tweakcn registry form..." and "a theme value that could end the declaration...", and the desktop smoke, which imports from a loopback URL through the page and refuses one that answers 404.
- Importing a tweakcn theme from its page URL (`/editor/theme?theme=<name>`, `/editor/theme/<id>` or `/themes/<id>`): the server reads the theme from tweakcn's registry on the same site rather than the page, and takes its whole design language, light and dark: colours, fonts, radius (the app's small, medium and large radii in proportion), the spacing unit, letter spacing and shadows, with a value dark draws differently held for dark alone. The theme's fonts are fetched once by the server from Google Fonts (latin woff2 only, bounded) and served to the clients at `GET /api/v1/themes/fonts/:fontId`, which add them with the FontFace API; a font that cannot be fetched is named and never refuses the theme. A page that is not a theme says what to paste instead: `server/test/themes.test.js`, `core/test/rules.test.js`, "a theme carries its whole design language...", `server/test/api.test.js`, "a theme font the server fetched...", and the desktop smoke, which pastes Elegant Luxury's editor URL (served from a loopback copy of tweakcn), puts it in force and reads its colours, type, radius, spacing and shadows back in light and dark.
- Every choice control (the System, Light, Dark switch and the text size chips) draws from one token pairing, on-accent words on the accent and muted words on the page surface, with the selected label marked from the same value that places the thumb; each label holds 4.5:1 against what it is drawn on: `core/test/rules.test.js`, "the System, Light, Dark switch and the text size chips read at 4.5:1...", and the desktop smoke, which measures every label in light and dark, in the default palette and in Elegant Luxury.
- A theme picker: a grid of cards, the default palette first, each drawn in its own theme's colours for the scheme in force, with the theme in force marked; choosing a card puts it in force on every client: `core/test/rules.test.js`, "the themes the server holds..." and "the default palette is offered on any element that asks for it...", and the desktop smoke, which reads a card's accent swatch back.
- The appearance switch: System, Light and Dark as one three-position control rather than a dropdown, held on the server so the choice survives a restart: `core/test/rules.test.js`, "there is no density setting...", `server/test/api.test.js`, "the appearance choice survives a server restart", and the desktop smoke.
- Text size as a percentage, 50% to 300%, scaling every type token on the page and in the chat list, with 100% writing nothing so it renders exactly what the tokens say. There is no density control: `core/test/rules.test.js`, "a text size percentage scales every type token...", and the desktop smoke, which measures the list and the page at 150% and back at 100%.
- A settings page that reads and writes the settings the server holds, and redraws when a change made anywhere arrives on the event stream; and, below phone width, one pane at a time with the list sliding in over the conversation and a way back: the desktop smoke.
- The settings page's schema, its defaults and what a control writes: `core/test/rules.test.js`, "the settings page draws the schema and writes the value a control gives".
- About is a page of its own on every platform, the same component on the desktop, the iPhone and Android, reached from the last row of Settings (back returns to Settings) and from the tray's and the app menu's About (back closes it). It opens with the app's icon, generated from `desktop/build/icon.svg` by the shared icon pipeline, its name and version, and Check for updates, which runs the tray's own check through the bridge's `updates.check` and shows the answer as the app notice; a phone, which does not update itself, says how its builds arrive. Below that are the details chela's About carries: the app's name and version, channel, build and commit, the server's version and commit, platform and architecture, Electron, Chromium and Node, where it was installed from, the rest of the build report, and links to the source, the licence and the issue tracker. Each value copies with a press, and the whole report copies for a bug report: `core/test/about-page.test.js`, `core/test/rules.test.js`, "the About section shows every field in chela's order, each from its own half", the desktop smoke ("about" and "tray"), which reads the page's structure at a phone's width and the desktop's and requires them to match, presses Check for updates and waits for the notice, and captures the page light and dark at both widths, and the phones' own About tests (`AboutPageTest.kt`, `AboutPageTests.swift`), which drive the real page through the real shell's bridge and keep a light and a dark capture.
- Settings is one sheet: a card only as wide as its content needs, a full-width top strip that is itself the back control (arrow, label and the Esc chip), sections with dividers and a one-line description each, and three ways back (the strip, Escape, and a press on the backdrop) that a press inside the card never triggers: `core/test/rules.test.js`, "a press leaves the sheet only when it both starts and ends on the backdrop", and the desktop smoke, which reads the strip's real hit area at its own corners and checks that the page does not scroll sideways at a narrow window, the About page included.
- The chat list sorted by activity or by name A to Z and Z to A, and filtered by unread, a named group, direct or group conversations and search terms, each a chip that refines the list by contact or by message text, with the arrangement and the person-made groups held on the server: `core/test/rules.test.js`, "the list sorts by activity, or by name A to Z and Z to A (issue 136)", "filters compose, clear one at a time, and search names and last messages", "Enter adds a search term, each term refines, and a chip can be removed or switch its mode (issue 133)", "groups keep their own order, draw as sections, and never lose an ungrouped chat"; `server/test/api.test.js`, "a chat arrangement is held on the server and read back on a reconnect".
- Edit selects chats to group, with an optional name, or to delete, and a delete is confirmed by sliding: `core/test/rules.test.js`, "grouping a selection takes an optional name, and an unnamed group gets the first free default (issue 137)", "slide to confirm only confirms at the end of the track, by drag or by key"; the desktop smoke drives both.
