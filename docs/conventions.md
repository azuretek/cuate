# Conventions

Every design decision Cuate has made that still holds, written as a rule with its reason, where it came from and what holds it. A rule is held by a test (named below by file and title), by a desktop smoke check (`smoke:<key>`, a key the smoke requires in `desktop/scripts/smoke.mjs`), or by review where neither can see it. `core/test/guards.test.js` "docs/conventions.md names a source for every rule, and every test and smoke check it cites exists" fails when a test named here is renamed or a smoke key is dropped, so this page cannot claim enforcement that has gone.

The design as built is [design.md](design.md); the contributor rules are [contributing.md](contributing.md); app notices have their own page, [app-notices.md](app-notices.md). New UI work names, in its pull request, the conventions here it follows or changes, and a change to a convention edits this page in the same pull request.

Status words: a rule with no status holds on main today. **Adopted, not yet built** means Abi has decided it and an open issue carries the work; until that issue closes, the behaviour it replaces is what ships. Decisions a later one replaced are listed at the end under [Superseded](#superseded), so nothing here contradicts what the app does.

## Values and tokens

- **Every value two surfaces share comes from the tokens.** Colour, type, spacing, radius, elevation, motion and icons live in `core/spec/tokens.json`, and `scripts/gen-tokens.mjs` writes `core/app/styles/tokens.css` from it. Why: a value written twice drifts, and an imported theme can only restyle what the tokens own. Source: #59, #61. Held by: `core/test/guards.test.js` "component CSS carries no literal colours or lengths"; `core/test/guards.test.js` "tokens.css is fresh"; `smoke:surface`.
- **A value several places must agree on lives in one spec under `core/spec/`** (the API, log events, tokens, the host bridge, naming, platforms). Why: code reads the spec and tests hold both sides to it, so the halves cannot disagree. Source: #1, #84. Held by: `core/test/guards.test.js` "the API spec is complete and consistent"; `core/test/build.test.js` "the server half is the server route model, so the two cannot drift".
- **No component writes a style attribute.** Custom properties are set with `style.setProperty` or chosen by an attribute selector. Why: the page's Content-Security-Policy drops inline style attributes, so one written in a template silently never applies. Source: #135, #145. Held by: `core/test/guards.test.js` "no component writes a style attribute, which the page's Content-Security-Policy drops".
- **Placeholder and hint text is dimmed, from the placeholder token, on every field.** One `::placeholder` rule draws every field's hint in `--color-placeholder`, which is the muted text colour of the scheme (and of an imported theme), at 4.5:1 on the page and the raised card. Why: a hint that reads at full strength looks like something you typed. Source: #185. Held by: `core/test/guards.test.js` "placeholder text is dimmed from its token, on every field"; `core/test/rules.test.js` "placeholder text is dimmed from its own token, legible on every field surface, and follows a theme (issue 185)"; `smoke:placeholder`.

## Theme and look

- **The look is a theme the server holds, not the platform's.** The palette is the Control UI's own; no system-blue accent, no platform font stack, no platform sheet or grouped-list chrome. A theme under `appearance.theme` overrides the same token set on every client without a rebuild. Why: the app should read the same on every device and stop looking like whichever platform it runs on. Source: #59, #61. Held by: `core/test/rules.test.js` "a theme turns into custom properties for the scheme in force"; `smoke:theme`.
- **The theme picker lists every theme the server holds, and previews each card in that theme's own colours.** The default card comes first, then every imported theme in the server's order, so no import is missing and two themes that share a name are two cards; each card's swatches are read from that theme's own tokens in the scheme in force, and a fresh Settings page repaints them once the sheet has drawn. Why: a card drawn from the active palette showed every other theme as the one in force, and an import keyed by its name alone let a new theme replace a different one, so the picker listed only the last. Source: #186. Held by: `core/test/rules.test.js` "every imported theme is held under its own id, so an import never silently replaces a different theme"; `core/test/rules.test.js` "two different themes never preview with the same swatches"; `core/test/theme-picker.test.js` "every card previews its own theme once the sheet has drawn it, in light"; `server/test/api.test.js` "every theme imported by URL is held and read back, however many there are and whatever they are named"; `smoke:themePicker`.
- **Nothing falls back to a platform accent.** The caret, native form controls and selected text take the theme's accent and selection colours; the iOS accent colour set is generated from the tokens; the Android launcher tile is the app icon's colour. Why: a system blue anywhere is a colour the theme did not choose. Source: #164, #165. Held by: `core/test/guards.test.js` "no shell wears a platform accent: the phone shells and the page take theirs from the tokens"; `smoke:surface`.
- **A theme is imported from its tweakcn page URL or a pasted export, and brings its whole design language** (colours, radius, fonts, shadows, letter spacing, spacing, light and dark). What it cannot carry is refused by name, never dropped silently, and a value that could escape its declaration or reach the network is refused. The server fetches; the client never loads from the network. Why: a theme that only carries colours is not the theme, and a silent drop hides what was lost. Source: #59, #100, #112, #132, #145. Held by: `core/test/rules.test.js` "a tweakcn theme is imported, and every name it cannot carry is refused out loud"; `core/test/rules.test.js` "a theme carries its whole design language: radius and spacing scales, shadows, letter spacing, and dark-only values"; `core/test/rules.test.js` "a theme value that could end the declaration or reach the network is refused"; `smoke:themeImport`, `smoke:themeUrl`, `smoke:themePage`.
- **Imported themes keep their semantic surface pairs.** Card and selection foregrounds survive an import in both schemes, and chat menus use the theme's shadow scale. Why: a background without its foreground draws unreadable text under some themes. Source: #159, #162. Held by: `core/test/chat-design.test.js` "tweakcn preserves semantic foregrounds in both schemes".
- **Light, dark or the system's, as a three-position switch; text size as a slider of percentages.** `appearance.skin` is System, Light, Dark; `appearance.textScale` is a slider whose stops are the schema's 50% to 300%, keyboard-operable, landing only on a stop, announcing the percentage rather than the index and showing the value beside the track, and it scales only the type tokens, writing nothing at 100%. There is no density control. Why: a dropdown hid a three-way choice, a point size meant nothing across devices, and density did nothing visible; the chips became a slider so a size is set by dragging or by a key (issue 244). Source: #112, #119, #244. Held by: `core/test/rules.test.js` "there is no density setting, and the skin and the text size are a switch and percentage choices (issue 112)"; `core/test/rules.test.js` "a text size percentage scales every type token, and 100% writes nothing"; `core/test/settings-tabs.test.js` "text size is a slider that lands only on the schema stops and announces the percentage"; `smoke:settings`.
- **Every segmented control and the text size reading read at 4.5:1 in both schemes**, the selected label in the on-accent colour, the rest in muted text, and the slider's percentage in the full text colour on the row it sits in. Why: the selected label vanished into its fill. Source: #135, #145, #244. Held by: `core/test/rules.test.js` "the System, Light, Dark switch and the text size reading read at 4.5:1 in both schemes of the default palette"; `smoke:choiceContrast`.
- **The surfaces read the theme's own palette through the surface roles, and every text pair drawn on a surface holds 4.5:1.** A direction for issue 217 lives in one block of `core/app/styles/roles.css`: each surface (the sidebar, a chat row, the composer field, a menu, a notice, a bubble, the search box and the chips) points at a palette token, so an imported theme restyles every surface and the direction is one remappable block. The chart colours earn their place here: the avatars cycle chart-1 to chart-5, the notices and received bubbles take a chart-2 tint, the menu hovers chart-3, the unread mark chart-1; the composer field is a lighter fill and the chat rows carry dividers. Why: the interface read as monotone and ignored most of the palette a theme carries. Source: #217. Held by: `core/test/roles.test.js` "the surface roles keep every text pair at 4.5:1 in both schemes of the default palette and an imported theme".
- **Icons are the sibling app's stroked set, drawn as masks from the tokens.** A control writes `<span class="icon" data-icon="…">`, never an SVG or a text glyph, and each glyph names the SF Symbol the iOS client draws. Why: one icon family across both apps, in the control's own colour under any theme. Source: #59, #154, #176. Held by: `core/test/guards.test.js` "every icon a component draws is one the icon set holds, and no control draws a text glyph for an icon"; `core/test/rules.test.js` "the icon set is drawn from the tokens, one stroked glyph per name, in the generated stylesheet"; `smoke:icons`.
- **Motion is the sibling app's**: the sheet and drawer curves, the screen push, the arrival spring sampled into `linear()`, and a floor on how long a transient state stays up. Reduced motion keeps every state and drops the animation. Why: the two clients should move alike, and a state shorter than the eye can catch is not shown. Source: #59, #75, #79, #154. Held by: `core/test/rules.test.js` "the motion tokens are the sibling app's, and the spring is recomputed rather than trusted".
- **One set of scrollbar styles, on the containers that scroll**, from tokens; a platform that draws overlay scrollbars keeps them. Why: a platform scrollbar inside a themed surface reads as a bug. Source: #85, #90, #139. Held by: `core/test/guards.test.js` "the scrollbars are one set, on the containers that scroll".
- **The send arrow fills its circle**, and the circle carries no ring of its own: the arrow is the shared icon set's stroked glyph (`arrow-up`), its size the button's own fraction (`--size-send-icon`) and its weight the glyph's stroke width, and the button's fill and the arrow's colour are the role tokens, so an imported theme restyles it and a size change carries both. It sits flush at the end of the composer row and is no larger than that row. Source: #87, #92, #216. Held by: `core/test/guards.test.js` "the send arrow takes its size and weight from the tokens, and its circle is the row's own"; `core/test/guards.test.js` "the send button is no larger than the composer row it sits in".
- **Images are dressed**: a preview at the picture's own aspect ratio with rounded corners, a soft shadow and a subtle edge, all from tokens. Source: #126, #129. Held by: `smoke:imagePreview`.
- **The app icon is Flor de muerto, drawn from two masters.** Two speech bubbles leaning on each other (the cuates), each a sugar skull with marigold eyes, a heart nose and a stitched smile: the master glyph in a 100 unit box (`core/spec/icon/flor-de-muerto.svg`) and a simplified one for 32 px and under (`flor-de-muerto-small.svg`: round eye holes, the nose, no teeth, cheeks or back nose, and a tight crop that fills the slot). Every detail is a true cut-out, the back bubble is parted from the front by a knocked-out gap rather than by colour, and no size is drawn by hand: one renderer (`core/app/rules/icon.js`) draws every image from the masters, and at 16 px a pixel whose centre falls in a cut-out is cleared so each still reads as a hole. Why: the shape has to survive grayscale, single-colour and template rendering, and a hand-drawn size drifts from the rest. Source: #189. Held by: `core/test/icon.test.js` "the masters are true cut-outs: eyes, nose, teeth and the gap between the bubbles are transparency"; `desktop/test/icon-images.test.js` "the renderer reads the masters as an SVG renderer does"; `core/test/icon.test.js` "the old chat bubble is gone: no fixed teal, and no hand-drawn per-size file".
- **Every colour in the icon comes from the active theme's tokens, through one pure function.** `iconPalette` reads accent, accent-fg, fg, bg, bg-raised, danger, badge and badge-fg for one scheme and gives the tile, the glyph, the back bubble and the badge. Light: the accent as a gentle vertical gradient, the glyph accent-fg where it reads at 2.6:1 on the accent and fg otherwise, the back bubble the glyph at 50%. Dark: bg-raised (a little lighter at the top) down to bg, the glyph the dark accent lightened step by step to 4:1 on bg-raised, the back bubble at 45%. Tinted and monochrome images are the glyph's alpha alone. A colour is parsed, never matched as text, so any CSS colour a theme carries, oklch() included, works. Every platform's generator and the desktop shell call the same function. Why: a fixed colour ignores the theme the person chose. Source: #189. Held by: `core/test/icon.test.js` "the palette derives every colour from the theme, and the glyph meets its contrast floor in both schemes"; `core/test/icon.test.js` "the palette reads any CSS colour a theme carries, oklch() included, and works on the parsed colour".
- **The unread badge is a solid red disc with a white count, and never vanishes into the tile.** The fill is the theme's `danger` where the count reads on it at 4.5:1 and it stands clear of every colour of the tile, otherwise the standard red the `badge` token carries; the count is the `badge-fg` token, always white. The Windows taskbar overlay is a disc that fills its square, drawn once per size the taskbar asks for, with the count exact to 9 and `9+` above. In the tray the count is drawn in white on the disc (the macOS template knocks it out, so macOS recolours the silhouette); the tray keeps its gap around the badge, and macOS's Dock and a Linux launcher draw their own badge from the same label the overlay draws (a plain dot at 16 px, one digit from 22 px, `9+` only from 32 px). iOS and Android draw their own badge over the app icon, from the count the shell gives them. Source: #189, #218. Held by: `core/test/icon.test.js` "the unread badge is a solid red disc with a white count that reads on it, never lost in the tile (issue 218)"; `core/test/icon.test.js` "the taskbar overlay fills its square with the badge, and its bold white count fits inside it (issue 218)"; `core/test/icon.test.js` "the template image at 16 and 32 px keeps its eyes and nose fully transparent, and knocks a gap around the badge"; `core/test/icon.test.js` "the count is a dot at 16 px, one digit from 22 px and 9+ only from 32 px"; `desktop/test/icon-images.test.js` "the badge reads the same way on every desktop: red with a white count, exact to 9 and 9+ above (issue 218)"; `smoke:overlayIcon`.
- **The desktop shell redraws its icons from the active theme.** The page reports the scheme it draws, the icon's tokens as it resolved them and the total unread through the `icon.redraw` bridge command, once per change; the shell redraws the tray image (a template image in the macOS menu bar), the window icon and the Windows taskbar overlay, and gives the Dock and a Linux launcher the count. A phone cannot recolour its icon at runtime and answers false. Source: #189. Held by: `desktop/test/icon-images.test.js` "the tray image changes when the theme or the scheme changes, and when the count crosses 0, 1 and 10"; `desktop/test/icon-images.test.js` "Windows carries the count on a taskbar overlay and Windows and Linux redraw the window icon from the theme"; `smoke:trayIcon`.
- **The original Orange icon is the default; Paper is its light counterpart, and the coloured choices carry the names Abi's palette sheet gave them.** Settings' App icon offers Orange first, and it is the default: the Flor de muerto masters through `iconPalette` in the default theme's light palette (`core/spec/tokens.json` `color.light`), the original terracotta reading as the app's own icon rather than a colour that shifts with the theme; it is the one colour the picker, the About picture and every generated asset carry, so the three cannot disagree (PR 257). Beside it are Paper (the light counterpart) and the five coloured alternatives the earlier palette sheet named in Mexican words: Azul, Rosa mexicano, Jade, Cempas\u00fachil and Morado (`core/spec/app-icons.json`), each the seven tokens the icon reads and the scheme it is drawn in, put through the same `iconPalette` and `renderIcon` over the same masters, so a fixed icon is the same glyph in other colours and never a second drawing. Follow theme remains a choice and draws the icon in the active theme's tokens. A fixed palette stands in for the theme in every image the desktop draws (the count still shows), and on the phones it is an alternate icon (iOS) or launcher alias (Android) the pipeline generates; Follow theme there is the store icon in the default theme, since neither phone can recolour an installed icon. Why: Abi asked for the original orange as the first icon in its dark rendering, a paper light one, the Mexican-named colours in place of Teal and Night, and the Night choice dropped (#246); the Teal and Night choices are gone. Source: #167, #189, #246. Held by: `core/test/settings-tabs.test.js` "the app icon is a setting the server holds, offered from the one spec: the original Orange first and the default (issue 246)"; `core/test/settings-tabs.test.js` "every fixed palette is the Flor de muerto masters coloured through the one palette, and ships on every platform"; `desktop/test/icon-images.test.js` "a fixed palette chosen in Settings draws every image whatever the theme and the scheme the page reports (issue 167)"; `smoke:appIcon`.
- **The sheet's way back reads at 4.5:1 in every theme.** The Settings/About top strip wears its own role off the theme's accent (`--role-back`, `--role-back-fg`, `--role-back-border`, `--role-back-hover` in `core/app/styles/roles.css`), so it shifts with every theme, the default and an imported one, rather than sitting flat on the card, and its label, its glyph, its rule and its Esc key hold 4.5:1 against the strip in light and dark. Why: under some themes the strip barely changed and under others it did not change at all, so it stopped reading as a control (#246). Source: #246. Held by: `core/test/roles.test.js` "the surface roles keep every text pair at 4.5:1 in both schemes of the default palette and an imported theme".
- **Every icon file is generated, and a stale one fails the build.** `desktop/scripts/icons.mjs` writes the desktop's `icon.png` and `icon.ico`, About's icon, the tray set, the iOS AppIcon set (light, dark and tinted) and the Android adaptive icon (the glyph as foreground at every density, the accent as background, and a monochrome layer for themed icons) from the masters and the default theme, and every fixed palette's picture, iOS alternate set and Android adaptive icon from `core/spec/app-icons.json`, and `--check` runs in `pnpm run build`. A theme cannot recolour an installed phone icon, so the stores carry the default theme's. The icon's size on a page is a token. Source: #171, #177, #189. Held by: `core/test/about-page.test.js` "the app icon on About is generated from the Flor de muerto masters by the shared icon pipeline"; `core/test/guards.test.js` "no shell wears a platform accent: the phone shells and the page take theirs from the tokens".

## Controls

- **Every button goes through the kit's one press behaviour** (`core/kit/press.js`). A press that starts work marks its control pending until the work settles, so a double press never starts it twice, then shows success or failure for a moment; repeat presses on an instant action are coalesced, never queued; a key-like control (an emoji) repeats. A component never disables a button to show it is busy. Why: every button should say what it is doing, and a repeated press must never send twice. Source: #140, #147. Held by: `core/test/guards.test.js` "every button in core/app goes through the kit press behaviour"; `core/test/press.test.js` "a double press runs the work once"; `core/test/press.test.js` "the states are drawn from tokens, and reduced motion animates none of them"; `smoke:sendOnce`, `smoke:importOnce`, `smoke:pressStates`.
- **Every action button shows pressed, working and outcome on itself, and never changes size.** The working state reads on the button (a spinner, or a label such as Checking), the outcome (Up to date, Copied) holds long enough to see from the motion tokens, and each label fits the same box. **Adopted, not yet built** for the size and named outcome labels (#190); the debounce and pending state already hold, above.
- **Standalone action buttons are centred in their card or page** (Check for updates, Copy diagnostics and the like). **Adopted, not yet built:** #190.
- **Copy is a real button**, the same shape as the others, never styled text. **Adopted, not yet built:** #190.
- **Icon buttons in a row match.** The sort, filter and settings buttons share size, hover and focus. Source: #136, #144. Held by: `smoke:sort`.
- **An icon button opens a small menu, and the menu's options are labelled.** The current choice is marked; no mode or state is spelled out as text inside a field. Source: #82, #136, #173. Held by: `core/test/rules.test.js` "the sort menu names its three choices, and every order has a label"; `smoke:header`.
- **A control that changes another control's behaviour stays attached to it.** The search mode is an arrow-only button flush against the left edge of the search field, one box with it and a divider between them, opening our own styled menu; no mode words sit on or beside the field itself. Source: #173. Held by: `smoke:header`.
- **No text label repeats what the layout already shows.** No heading above the chat list, no "Reply to X" label, no quote of the message being answered above the composer, no mode text in a field. Why: repeated text competes with the conversation. Source: #82, #159, #169, #183. Held by: `core/test/conversation-press.test.js` "a received reply is drawn from its stored pointer and never shows the original body or a reply-to label, its original not loaded included"; `smoke:header`.
- **Only a destructive action asks to be sure, and it asks with a slide.** Grouping acts on the first press; delete opens a confirm on the sheet backdrop naming how many chats, confirmed only by sliding to the end of the track (or by key). Deleting hides the client's entry; no message is touched. Source: #110, #113, #137, #144. Held by: `core/test/rules.test.js` "the group actions act on the first press, and the confirm modal is the only delete gate"; `core/test/rules.test.js` "slide to confirm only confirms at the end of the track, by drag or by key"; `smoke:editMode`.
- **A name the person may skip is optional.** A group's name prompt can be left empty, and an unnamed group gets the first free default. Source: #137. Held by: `core/test/rules.test.js` "grouping a selection takes an optional name, and an unnamed group gets the first free default (issue 137)".
- **A control holds one line.** A label never wraps at any supported width or text size; it shortens instead. Source: #122, #124. Held by: `smoke:editLine`.

## Panels, sheets and dismissal

- **Every popover, menu and modal panel closes on a press outside it and on Escape, through one kit behaviour** (`core/kit/dismiss.js`). The closing press is consumed, so the control underneath never fires; a press on the panel's own trigger is left to its toggle; Escape closes only the topmost panel, before a focused field sees the key; stacked panels close from the top down. Why: each panel had its own way to close, and an outside press also opened whatever was underneath. Source: #111, #170, #178. Held by: `core/test/guards.test.js` "every popover and modal panel dismisses through the kit"; `core/test/dismiss.test.js` "a press outside an open panel closes it, and the control underneath never sees that press or its click"; `core/test/dismiss.test.js` "stacked panels: Escape closes the top one only, and a press inside the top one closes nothing beneath it"; `smoke:dismiss`.
- **Settings and About arrive as a sheet**: a card only as wide as its content needs, whose whole top strip is the back control (arrow, label, Esc chip), with a press on the backdrop as a second way back. A press that starts inside and ends outside does not close it. Source: #79, #111, #114. Held by: `core/test/rules.test.js` "a press leaves the sheet only when it both starts and ends on the backdrop"; `smoke:sheet`.
- **Every close (X) control is one shared control, and a press anywhere on its drawn circle closes.** The image viewer, the thread card and every notice draw their X through `core/app/components/close-button.js`: the button is its own hit area, a square around the circle it draws, sized from a token, and nothing is drawn over it. It takes no window drag, and neither does any backdrop or notice card, because on the frameless desktop window a press inside a header's drag region moves the window and never reaches the page, whatever is drawn over that spot. Why: the viewer's X sat over the contact header's drag strip, so it answered only where it overlapped the window controls, and the thread's X in the header read as closing the conversation. Source: #213. Held by: `core/test/guards.test.js` "every close control is the shared close button, whose whole circle takes the press"; `smoke:closeControls`.
- **The image viewer's X is placed from the viewer, never from the contact header or the name/group banner.** The viewer owns the whole window, so its close control is measured from the viewer's own top-right corner, a margin in from the true window edge, clear of the platform's top chrome: macOS's traffic-light strip, and the window controls Windows and Linux draw in that corner. It is never laid out from the contact header, so it can never read as sitting on the blurred banner behind the picture, and it stays reachable at every window size, portrait or landscape, wider than the window or zoomed. While the viewer is open the two headers give up their window drag, so the X never sits in a drag region at all, not even one the no-drag backdrop already cancels. Why: maximised, the X floated at the right edge level with the header and read as part of the banner. Source: #245. Held by: `core/test/viewer-close.test.js` "the viewer X is placed from the viewer and the platform chrome, never the contact header"; `core/test/viewer-close.test.js` "no viewer close rule is laid out from the contact header or the name banner"; `core/test/viewer-close.test.js` "the viewer X carries no drag, and the backdrop under it is no-drag"; `core/test/viewer-close.test.js` "the headers give up their window drag while the viewer is open"; `smoke:closeControls`.
- **A sheet, a confirm and the image viewer share one blurred and darkened backdrop.** Why: one treatment for "something is over the app". Source: #126, #137. Held by: `smoke:imageViewer`.
- **Every popover wears a caret pointing at the control that opened it, drawn as the panel's own edge.** A menu, picker or panel marks itself with `data-popover` and the edge its caret sits on; one stylesheet rule draws the triangle and `core/kit/popover.js` aims it at that control (read from the same dismiss pair the panel already declares), so a new menu gets its caret for free. Every menu and panel surface in the app carries the caret, the emoji panel and the attachment menu included, and none draws a second one by hand; the triangle is sized from the one `--size-caret` token (14px, the same value at desktop and the phone width) and drawn the whole of it, with a real tip rather than a dot; its outline carries the panel's border token at the panel's own one border weight and its fill the panel's surface token, so it is the panel's edge raised and never a hard-coded colour; and each base sits `--caret-overlap` (exactly one border width) inside the panel with the inner fill spanning the whole `--size-caret` at its base, so the panel's border is NOT drawn across the span the caret occupies and its edge becomes the triangle's two sides with no seam, no gap and no double line. Why: a menu floating unanchored read as detached from the control it acted on, a caret too small or stuck on the edge did not read as the panel's own corner, and a panel border left to cross the caret's span showed as a line through the join. Source: #217, #251. Held by: `core/test/guards.test.js` "every menu, popover and picker wears the shared caret"; `core/test/guards.test.js` "the caret is sized and coloured from the panel tokens, overlapping it by exactly one border"; `core/test/popover.test.js` "an untargeted placement is refused: a control that is not over the popover answers null"; `core/test/popover.test.js` "the caret is kept whole by half its drawn width, so a corner or a screen edge never overhangs it"; `smoke:carets`.
- **A popover drawn inside a drag strip takes its own presses.** `-webkit-app-region` is inherited: the chats header, the conversation header and the composer bar are `drag`, so every menu drawn inside one computes to `drag` and a real press on an option moves the window and never reaches the page, while a scripted click still works. Every `[data-popover]` is therefore `no-drag`, which punches a hole in the strip for the panel and its options; the header's own controls keep their own `no-drag`. Why: the search-mode, sort and filter menus opened on a click but no option could be chosen, and neither a scripted click nor a synthetic event could see the fault. Source: #251. Held by: `core/test/guards.test.js` "a popover is no-drag, so a menu inside a drag header takes its own presses"; `smoke:headerMenus`.
- **Settings are grouped into sections with dividers and a one-line description each**, from one list of groups. Source: #78, #111. Held by: `core/test/rules.test.js` "the settings page draws the schema and writes the value a control gives".

## Pages and navigation

- **Mobile and desktop offer the same pages.** About is its own page on every platform, the same component in the sheet's chrome; Settings draws an About row at the bottom of every page that pushes it, and back returns to Settings; the tray's and the app menu's About open it directly and back closes it. ## Notices and updates

Desktop cards enter from the right beneath the controls; phone cards take a band at the top inside the safe area. Why: a full-width banner covered the app and repeated itself. Source: #160, #161; [app-notices.md](app-notices.md). Held by: `core/test/app-notices.test.js` "duplicate events are silent and progress replaces one operation"; `core/test/app-notices.test.js` "notice geometry clears safe areas, controls and composer with directional reduced motion"; `smoke:notices`.
- **Notices draw above every surface**, the highest layer in the stylesheet above the media viewer, the thread view, sheets and About, while still starting below the header that carries the window controls, so a press on any surface sees its answer and the controls are never covered. Source: #171, #177, #191. Held by: `core/test/app-notices.test.js` "the notice stack draws above every other surface and starts below the header and its window controls". **Adopted, not yet built:** a close control and a mark-as-read that clears the notice on every device through the server (#191).
- **Chat message notifications keep their native route** and never enter the app notice surface. Source: #160, #161.
- **Every notice type has its own switch, held on the server**, and a type switched off never fires; one release is announced once. Source: #62, #78, #97. Held by: `core/test/rules.test.js` "every notice type has its own switch and a notice only fires when it is on"; `core/test/rules.test.js` "one release is announced once, however many checks report it".
- **An update is checked at start, never downloaded unless automatic download is on** (off by default), and can be installed from the notice inside the app. Source: #62, #68, #69, #88, #95. Held by: `smoke:updates`.
- **Phones update the sibling app's way**: iOS reads the release feed and links to TestFlight when a newer build exists on the running build's own channel and build; Android downloads the newer signed APK, verifies its size and SHA-256 against the release manifest and its signer against both the manifest and the installed app, and hands it to the system installer with the person's confirmation, both reporting through the notice and the button. Source: #192. Held by: `core/test/about-page.test.js` "a phone reads the release feed through its shell and offers a newer build the way it installs"; `core/test/about-page.test.js` "a phone on the newest build is told so, and a feed it cannot read fails the press with the reason"; `core/test/phone-updates.test.js` "version comparison: a newer build is offered, the same or an older one is not"; `core/test/phone-updates.test.js` "TestFlight link: an iOS release is offered with the action that opens TestFlight"; `core/test/phone-updates.test.js` "APK download and verification: the manifest the release carries is checked before an APK is trusted".

## Behaviour every surface keeps

- **Resizing keeps your place**: every scrolled view anchors to an item through `core/kit/scroll.js`, and the open conversation, selection, composer text and caret, and any open menu survive a resize, a rotation or a text size change. Full text: [design.md](design.md#conventions-every-surface-keeps). Source: #142, #147. Held by: `core/test/guards.test.js` "every scrolled view keeps its place through the kit"; `core/test/scroll.test.js` "a resize that rewraps every item keeps the item at the top of the view"; `core/test/scroll.test.js` "a scroll the browser makes while a turn relays the view out never moves the place" (#211); `smoke:resizeKeeps`.
- **Switching conversations returns each to the place you left it, at once.** The page holds each conversation it has opened, so a switch back draws it from what it holds rather than waiting on the server, and each conversation keeps its own place through `core/app/rules/places.js`: one left at its newest message comes back to the end (a message that arrived while you were away stays the one you land on), one scrolled up comes back to the same message at the same height within two pixels, and one never opened opens at its newest message. Why: a switch looked dead while the next page was fetched, and coming back to a conversation dropped the reader somewhere they had not scrolled to. Source: #200. Held by: `core/test/chat-switch.test.js` "leaving a conversation remembers its place, and entering one comes back to that place"; `core/test/chat-switch.test.js` "a conversation never opened, and one whose place has gone, opens at its newest message"; `smoke:switchPlace`, `smoke:switchInstant`.
- **Nothing refreshes or shows a loading page**: data is replaced in place in one step, and the only full-screen wait is the very first connection. Source: #142, #147. Held by: `core/test/guards.test.js` "nothing reloads the page or clears a list before its replacement arrives"; `smoke:noBlank`, `smoke:resyncKeeps`.
- **The Android shell keeps its page** through rotation, split-screen, the keyboard and dark mode. Source: #142, #147. Held by: `core/test/guards.test.js` "the Android shell keeps its page through rotation and resizing".
- **Settings, sort order and groups live on the server**, so a choice made on one device reaches every device on the event stream, and a late write answer never rolls back a streamed change. Source: #47, #73, #99. Held by: `core/test/rules.test.js` "a late write answer never rolls back a change the event stream already delivered"; `smoke:settings`.
- **A design change is validated on every platform and in both schemes**: the smoke asserts the tokens the page resolves in light and dark on macOS, Windows and Linux, and the phones run their own legs. Source: #64, #65. Held by: `desktop/test/desktop-platforms.test.js` "the desktop smoke asserts the rendered tokens, in both schemes"; `smoke:surface`.

## The engine link

- **An engine link is connected only when it is.** The child is alive, the engine answered status with a readable Messages database, and the watch is subscribed (an engine too old to know the method is not held back by it); readiness is a gate in `server/src/engine/link.js`, not a guess, and a link that is up for a moment and then dies was never connected. Source: #271. Held by: `server/test/engine-link.test.js` "readiness needs a live child, a readable database and a subscribed watch".
- **An engine restart backs off, and the backoff resets only after the link has STAYED ready.** A single successful status does not reset it, so an engine that is up for a moment and then dies cannot be restarted every second; the delay doubles to a cap and returns to the minimum only after the link has been ready for a minute. Source: #271. Held by: `server/test/engine-link.test.js` "the backoff doubles while the link cannot stay up and resets only after it has stayed ready".
- **The engine adapter runs ONE child.** A start joins a start already in flight and never replaces a live child; only an explicit restart replaces one, so the adapter's own restart and the watchdog cannot each spawn a child for the same broken engine. Source: #271. Held by: `server/test/engine-link.test.js` "two starts at once spawn one child, and ensure leaves a connected child alone".
- **An engine failure is never swallowed.** Every request logs its method, its duration and its outcome; a failure logs the engine's own code and message; the child's exit logs its code or signal, its uptime, its last stderr line, and what it was restarting away from; and a dead link refuses an HTTP read with a 5xx rather than answering from a stale copy. Source: #271. Held by: `server/test/engine-link.test.js` "an engine failure is surfaced as a refusal and a log line, never swallowed".
- **An in-flight engine request is answered when its child is replaced, never dropped.** A request in flight when the child exits or is replaced is rejected with `engine_exit`, so the caller gets an outcome it can act on. Source: #271. Held by: `server/test/engine-link.test.js` "a request in flight when the child exits is answered with engine_exit, not dropped".
