# Conventions

Every design decision Cuate has made that still holds, written as a rule with its reason, where it came from and what holds it. A rule is held by a test (named below by file and title), by a desktop smoke check (`smoke:<key>`, a key the smoke requires in `desktop/scripts/smoke.mjs`), or by review where neither can see it. `core/test/guards.test.js` "docs/conventions.md names a source for every rule, and every test and smoke check it cites exists" fails when a test named here is renamed or a smoke key is dropped, so this page cannot claim enforcement that has gone.

The design as built is [design.md](design.md); the contributor rules are [contributing.md](contributing.md); app notices have their own page, [app-notices.md](app-notices.md). New UI work names, in its pull request, the conventions here it follows or changes, and a change to a convention edits this page in the same pull request.

Status words: a rule with no status holds on main today. **Adopted, not yet built** means Abi has decided it and an open issue carries the work; until that issue closes, the behaviour it replaces is what ships. Decisions a later one replaced are listed at the end under [Superseded](#superseded), so nothing here contradicts what the app does.

## Values and tokens

- **Every value two surfaces share comes from the tokens.** Colour, type, spacing, radius, elevation, motion and icons live in `core/spec/tokens.json`, and `scripts/gen-tokens.mjs` writes `core/app/styles/tokens.css` from it. Why: a value written twice drifts, and an imported theme can only restyle what the tokens own. Source: #59, #61. Held by: `core/test/guards.test.js` "component CSS carries no literal colours or lengths"; `core/test/guards.test.js` "tokens.css is fresh"; `smoke:surface`.
- **A value several places must agree on lives in one spec under `core/spec/`** (the API, log events, tokens, the host bridge, naming, platforms). Why: code reads the spec and tests hold both sides to it, so the halves cannot disagree. Source: #1, #84. Held by: `core/test/guards.test.js` "the API spec is complete and consistent"; `core/test/build.test.js` "the server half is the server route model, so the two cannot drift".
- **No component writes a style attribute.** Custom properties are set with `style.setProperty` or chosen by an attribute selector. Why: the page's Content-Security-Policy drops inline style attributes, so one written in a template silently never applies. Source: #135, #145. Held by: `core/test/guards.test.js` "no component writes a style attribute, which the page's Content-Security-Policy drops".
- **Placeholder and hint text is dimmed, from the placeholder token, on every field.** One `::placeholder` rule draws every field's hint in `--color-placeholder`, which is the muted text colour of the scheme (and of an imported theme), at 4.5:1 on the page and the raised card. Why: a hint that reads at full strength looks like something you typed. Source: #185. Held by: `core/test/guards.test.js` "placeholder text is dimmed from its token, on every field"; `core/test/rules.test.js` "placeholder text is dimmed from its own token, legible on every field surface, and follows a theme (issue 185)"; `smoke:placeholder`.

## Theme and look

- **The look is a theme the server holds, not the platform's.** The palette is the Control UI's own; no system-blue accent, no platform font stack, no platform sheet or grouped-list chrome. A theme under `appearance.theme` overrides the same token set on every client without a rebuild. Why: the app should read the same on every device and stop looking like whichever platform it runs on. Source: #59, #61. Held by: `core/test/rules.test.js` "a theme turns into custom properties for the scheme in force"; `smoke:theme`.
- **Nothing falls back to a platform accent.** The caret, native form controls and selected text take the theme's accent and selection colours; the iOS accent colour set is generated from the tokens; the Android launcher tile is the app icon's colour. Why: a system blue anywhere is a colour the theme did not choose. Source: #164, #165. Held by: `core/test/guards.test.js` "no shell wears a platform accent: the phone shells and the page take theirs from the tokens"; `smoke:surface`.
- **A theme is imported from its tweakcn page URL or a pasted export, and brings its whole design language** (colours, radius, fonts, shadows, letter spacing, spacing, light and dark). What it cannot carry is refused by name, never dropped silently, and a value that could escape its declaration or reach the network is refused. The server fetches; the client never loads from the network. Why: a theme that only carries colours is not the theme, and a silent drop hides what was lost. Source: #59, #100, #112, #132, #145. Held by: `core/test/rules.test.js` "a tweakcn theme is imported, and every name it cannot carry is refused out loud"; `core/test/rules.test.js` "a theme carries its whole design language: radius and spacing scales, shadows, letter spacing, and dark-only values"; `core/test/rules.test.js` "a theme value that could end the declaration or reach the network is refused"; `smoke:themeImport`, `smoke:themeUrl`, `smoke:themePage`.
- **Imported themes keep their semantic surface pairs.** Card and selection foregrounds survive an import in both schemes, and chat menus use the theme's shadow scale. Why: a background without its foreground draws unreadable text under some themes. Source: #159, #162. Held by: `core/test/chat-design.test.js` "tweakcn preserves semantic foregrounds in both schemes".
- **Light, dark or the system's, as a three-position switch; text size as a percentage.** `appearance.skin` is System, Light, Dark; `appearance.textScale` offers 50% to 300% and scales only the type tokens, writing nothing at 100%. There is no density control. Why: a dropdown hid a three-way choice, a point size meant nothing across devices, and density did nothing visible. Source: #112, #119. Held by: `core/test/rules.test.js` "there is no density setting, and the skin and the text size are a switch and percentage choices (issue 112)"; `core/test/rules.test.js` "a text size percentage scales every type token, and 100% writes nothing"; `smoke:settings`.
- **Every segmented control and choice chip reads at 4.5:1 in both schemes**, the selected label in the on-accent colour and the rest in muted text. Why: the selected label vanished into its fill. Source: #135, #145. Held by: `core/test/rules.test.js` "the System, Light, Dark switch and the text size chips read at 4.5:1 in both schemes of the default palette"; `smoke:choiceContrast`.
- **Icons are the sibling app's stroked set, drawn as masks from the tokens.** A control writes `<span class="icon" data-icon="…">`, never an SVG or a text glyph, and each glyph names the SF Symbol the iOS client draws. Why: one icon family across both apps, in the control's own colour under any theme. Source: #59, #154, #176. Held by: `core/test/guards.test.js` "every icon a component draws is one the icon set holds, and no control draws a text glyph for an icon"; `core/test/rules.test.js` "the icon set is drawn from the tokens, one stroked glyph per name, in the generated stylesheet"; `smoke:icons`.
- **Motion is the sibling app's**: the sheet and drawer curves, the screen push, the arrival spring sampled into `linear()`, and a floor on how long a transient state stays up. Reduced motion keeps every state and drops the animation. Why: the two clients should move alike, and a state shorter than the eye can catch is not shown. Source: #59, #75, #79, #154. Held by: `core/test/rules.test.js` "the motion tokens are the sibling app's, and the spring is recomputed rather than trusted".
- **One set of scrollbar styles, on the containers that scroll**, from tokens; a platform that draws overlay scrollbars keeps them. Why: a platform scrollbar inside a themed surface reads as a bug. Source: #85, #90, #139. Held by: `core/test/guards.test.js` "the scrollbars are one set, on the containers that scroll".
- **The send arrow fills its circle**, its size and weight from tokens that scale with the button. Source: #87, #92. Held by: `core/test/guards.test.js` "the send arrow takes its size and weight from tokens".
- **Images are dressed**: a preview at the picture's own aspect ratio with rounded corners, a soft shadow and a subtle edge, all from tokens. Source: #126, #129. Held by: `smoke:imagePreview`.
- **The app icon is Flor de muerto, drawn from two masters.** Two speech bubbles leaning on each other (the cuates), each a sugar skull with marigold eyes, a heart nose and a stitched smile: the master glyph in a 100 unit box (`core/spec/icon/flor-de-muerto.svg`) and a simplified one for 32 px and under (`flor-de-muerto-small.svg`: round eye holes, the nose, no teeth, cheeks or back nose, and a tight crop that fills the slot). Every detail is a true cut-out, the back bubble is parted from the front by a knocked-out gap rather than by colour, and no size is drawn by hand: one renderer (`core/app/rules/icon.js`) draws every image from the masters, and at 16 px a pixel whose centre falls in a cut-out is cleared so each still reads as a hole. Why: the shape has to survive grayscale, single-colour and template rendering, and a hand-drawn size drifts from the rest. Source: #189. Held by: `core/test/icon.test.js` "the masters are true cut-outs: eyes, nose, teeth and the gap between the bubbles are transparency"; `desktop/test/icon-images.test.js` "the renderer reads the masters as an SVG renderer does"; `core/test/icon.test.js` "the old chat bubble is gone: no fixed teal, and no hand-drawn per-size file".
- **Every colour in the icon comes from the active theme's tokens, through one pure function.** `iconPalette` reads accent, accent-fg, fg, bg, bg-raised, danger and danger-fg for one scheme and gives the tile, the glyph, the back bubble and the badge. Light: the accent as a gentle vertical gradient, the glyph accent-fg where it reads at 2.6:1 on the accent and fg otherwise, the back bubble the glyph at 50%. Dark: bg-raised (a little lighter at the top) down to bg, the glyph the dark accent lightened step by step to 4:1 on bg-raised, the back bubble at 45%. Tinted and monochrome images are the glyph's alpha alone. A colour is parsed, never matched as text, so any CSS colour a theme carries, oklch() included, works. Every platform's generator and the desktop shell call the same function. Why: a fixed colour ignores the theme the person chose. Source: #189. Held by: `core/test/icon.test.js` "the palette derives every colour from the theme, and the glyph meets its contrast floor in both schemes"; `core/test/icon.test.js` "the palette reads any CSS colour a theme carries, oklch() included, and works on the parsed colour".
- **The unread badge never vanishes into the tile.** It is danger with danger-fg text, unless the accent is saturated and within 40 degrees of danger's hue (the default theme is), when it is the scheme's fg with whichever of bg and fg reads on it. On the app icon (the Windows taskbar overlay) it carries a ring in the background colour; in the tray it is knocked out of the glyph with a gap and its digit is knocked out of it, so it holds in a template image: a plain dot at 16 px, one digit from 22 px, 9+ only from 32 px. iOS, macOS's Dock and Android draw their own badge over the app icon, from the count the shell gives them. Source: #189. Held by: `core/test/icon.test.js` "the badge never lands within 40 degrees of hue of the tile, and the default theme gets the neutral badge"; `core/test/icon.test.js` "the template image at 16 and 32 px keeps its eyes and nose fully transparent, and knocks a gap around the badge"; `core/test/icon.test.js` "the count is a dot at 16 px, one digit from 22 px and 9+ only from 32 px".
- **The desktop shell redraws its icons from the active theme.** The page reports the scheme it draws, the icon's tokens as it resolved them and the total unread through the `icon.redraw` bridge command, once per change; the shell redraws the tray image (a template image in the macOS menu bar), the window icon and the Windows taskbar overlay, and gives the Dock and a Linux launcher the count. A phone cannot recolour its icon at runtime and answers false. Source: #189. Held by: `desktop/test/icon-images.test.js` "the tray image changes when the theme or the scheme changes, and when the count crosses 0, 1 and 10"; `desktop/test/icon-images.test.js` "Windows carries the count on a taskbar overlay and Windows and Linux redraw the window icon from the theme"; `smoke:trayIcon`.
- **Every icon file is generated, and a stale one fails the build.** `desktop/scripts/icons.mjs` writes the desktop's `icon.png` and `icon.ico`, About's icon, the tray set, the iOS AppIcon set (light, dark and tinted) and the Android adaptive icon (the glyph as foreground at every density, the accent as background, and a monochrome layer for themed icons) from the masters and the default theme, and `--check` runs in `pnpm run build`. A theme cannot recolour an installed phone icon, so the stores carry the default theme's. The icon's size on a page is a token. Source: #171, #177, #189. Held by: `core/test/about-page.test.js` "the app icon on About is generated from the Flor de muerto masters by the shared icon pipeline"; `core/test/guards.test.js` "no shell wears a platform accent: the phone shells and the page take theirs from the tokens".

## Controls

- **Every button goes through the kit's one press behaviour** (`core/kit/press.js`). A press that starts work marks its control pending until the work settles, so a double press never starts it twice, then shows success or failure for a moment; repeat presses on an instant action are coalesced, never queued; a key-like control (an emoji) repeats. A component never disables a button to show it is busy. Why: every button should say what it is doing, and a repeated press must never send twice. Source: #140, #147. Held by: `core/test/guards.test.js` "every button in core/app goes through the kit press behaviour"; `core/test/press.test.js` "a double press runs the work once"; `core/test/press.test.js` "the states are drawn from tokens, and reduced motion animates none of them"; `smoke:sendOnce`, `smoke:importOnce`, `smoke:pressStates`.
- **Every action button shows pressed, working and outcome on itself, and never changes size.** The working state reads on the button (a spinner, or a label such as Checking), the outcome (Up to date, Copied) holds long enough to see from the motion tokens, and each label fits the same box. **Adopted, not yet built** for the size and named outcome labels (#190); the debounce and pending state already hold, above.
- **Standalone action buttons are centred in their card or page** (Check for updates, Copy diagnostics and the like). **Adopted, not yet built:** #190.
- **Copy is a real button**, the same shape as the others, never styled text. **Adopted, not yet built:** #190.
- **Icon buttons in a row match.** The sort, filter and settings buttons share size, hover and focus. Source: #136, #144. Held by: `smoke:sort`.
- **An icon button opens a small menu, and the menu's options are labelled.** The current choice is marked; no mode or state is spelled out as text inside a field. Source: #82, #136, #173. Held by: `core/test/rules.test.js` "the sort menu names its three choices, and every order has a label". **Adopted, not yet built** for the search mode, which still has its own selector and per-chip mode text (#173).
- **A control that changes another control's behaviour stays attached to it.** The search mode button sits inside or flush against the search field as one control, not a separate floating button. Source: #173. **Adopted, not yet built:** #173.
- **No text label repeats what the layout already shows.** No heading above the chat list, no "Reply to X" label, no quote of the message being answered above the composer, no mode text in a field. Why: repeated text competes with the conversation. Source: #82, #159, #169, #183. Held by: `core/test/conversation-press.test.js` "a received reply carries one thread line and never the original body or a reply-to label, its original not loaded included"; `smoke:header`.
- **Only a destructive action asks to be sure, and it asks with a slide.** Grouping acts on the first press; delete opens a confirm on the sheet backdrop naming how many chats, confirmed only by sliding to the end of the track (or by key). Deleting hides the client's entry; no message is touched. Source: #110, #113, #137, #144. Held by: `core/test/rules.test.js` "the group actions act on the first press, and the confirm modal is the only delete gate"; `core/test/rules.test.js` "slide to confirm only confirms at the end of the track, by drag or by key"; `smoke:editMode`.
- **A name the person may skip is optional.** A group's name prompt can be left empty, and an unnamed group gets the first free default. Source: #137. Held by: `core/test/rules.test.js` "grouping a selection takes an optional name, and an unnamed group gets the first free default (issue 137)".
- **A control holds one line.** A label never wraps at any supported width or text size; it shortens instead. Source: #122, #124. Held by: `smoke:editLine`.

## Panels, sheets and dismissal

- **Every popover, menu and modal panel closes on a press outside it and on Escape, through one kit behaviour** (`core/kit/dismiss.js`). The closing press is consumed, so the control underneath never fires; a press on the panel's own trigger is left to its toggle; Escape closes only the topmost panel, before a focused field sees the key; stacked panels close from the top down. Why: each panel had its own way to close, and an outside press also opened whatever was underneath. Source: #111, #170, #178. Held by: `core/test/guards.test.js` "every popover and modal panel dismisses through the kit"; `core/test/dismiss.test.js` "a press outside an open panel closes it, and the control underneath never sees that press or its click"; `core/test/dismiss.test.js` "stacked panels: Escape closes the top one only, and a press inside the top one closes nothing beneath it"; `smoke:dismiss`.
- **Settings and About arrive as a sheet**: a card only as wide as its content needs, whose whole top strip is the back control (arrow, label, Esc chip), with a press on the backdrop as a second way back. A press that starts inside and ends outside does not close it. Source: #79, #111, #114. Held by: `core/test/rules.test.js` "a press leaves the sheet only when it both starts and ends on the backdrop"; `smoke:sheet`.
- **A sheet, a confirm and the image viewer share one blurred and darkened backdrop.** Why: one treatment for "something is over the app". Source: #126, #137. Held by: `smoke:imageViewer`.
- **Settings are grouped into sections with dividers and a one-line description each**, from one list of groups. Source: #78, #111. Held by: `core/test/rules.test.js` "the settings page draws the schema and writes the value a control gives".

## Pages and navigation

- **Mobile and desktop offer the same pages.** About is its own page on every platform, the same component in the sheet's chrome; Settings ends with an About row that pushes it, and back returns to Settings; the tray's and the app menu's About open it directly and back closes it. Source: #171, #177. Held by: `core/test/about-page.test.js` "About opened from Settings is pushed over it, and its back returns to Settings"; `core/test/about-page.test.js` "About opened on its own (the tray, the app menu) closes the sheet on back"; `smoke:about`.
- **Mobile offers every desktop setting, in tabs, one per section.** **Adopted, not yet built:** #167.
- **About says exactly what is running, on both halves**: version, channel, build, commit and date for the client (from the shell) and the server (from the server), runtimes, platform and install source, a stated mismatch when the halves differ, and one Copy for the whole block. Why: a bug report can quote it and nobody guesses which build is running. Source: #84, #96, #134, #143. Held by: `core/test/build.test.js` "the client version comes from the shell and the server version from the server"; `core/test/build.test.js` "a pair on different commits is stated, and an unmatched pair is never called a match"; `core/test/build.test.js` "the one action copies the whole block".
- **About offers Check for updates**, the same check the tray runs, answered through the app notice. Source: #171, #177. Held by: `core/test/about-page.test.js` "Check for updates asks the shell for the same check the tray runs and shows its answer as the app notice".
- **Below phone width one pane shows at a time**, the chat list sliding in from the left over the conversation like the sibling's slide menus, with a way back. Source: #47, #50, #53, #55. Held by: `smoke:phone`, `smoke:phoneDrawer`.
- **The chats panel opens and closes with a drag from the left edge only**, following the finger and settling by where it ended; a drag elsewhere stays a scroll or a selection; reduced motion still tracks the finger. Source: #71, #75. Held by: `core/test/drawer.test.js` "only the left edge opens the list"; `core/test/drawer.test.js` "a vertical move is a scroll, never the drawer"; `smoke:phoneEdgeOnly`, `smoke:phoneSettle`, `smoke:phoneReduced`.
- **Nothing overflows the phone's width**, with or without the keyboard; the send control stays whole. Source: #53, #55. Held by: `smoke:phoneFits`, `smoke:phoneSend`.
- **The way back to the chats list on mobile is a chats icon, not a back arrow**, with a label naming the destination. **Adopted, not yet built:** #168.
- **The conversation header stays pinned**, so who you are answering and the way back are always in view: the document never scrolls as a whole, only the messages do. Source: #180, #179. Held by: `core/test/system-bars.test.js` "the page never scrolls or zooms as a whole, so the header stays pinned on every platform"; `smoke:headerPinned`.
- **The chat list header is a search field and icons, with no heading text.** Search filters live; Enter turns the text into a term chip and each later term refines; filter and sort are icon menus; the gear opens Settings. Source: #82, #89, #133, #144. Held by: `core/test/rules.test.js` "Enter adds a search term, each term refines, and a chip can be removed or switch its mode (issue 133)"; `smoke:searchTerms`, `smoke:header`.
- **Edit is a small text control** that turns on a checkbox per chat and a bar of Group, Delete and Done. Source: #137, #144. Held by: `core/test/rules.test.js` "a selection counts, selects all and clears together, and agrees with the rows on screen"; `smoke:editMode`.
- **The list sorts by recent activity, or by name A to Z or Z to A**, locale-aware, and the choice follows the account. Filters compose and clear one at a time; a chat in no group is still shown; a filter matching nothing says so. Source: #73, #76, #136. Held by: `core/test/rules.test.js` "the list sorts by activity, or by name A to Z and Z to A (issue 136)"; `core/test/rules.test.js` "filters compose, clear one at a time, and search names and last messages"; `core/test/rules.test.js` "groups keep their own order, draw as sections, and never lose an ungrouped chat".

## Messages and the conversation

- **Long press, a long click or a right click is the way to a message's actions.** One menu shows the received time, Reply in thread and React as icons from the shared set; a message carries no buttons of its own. Source: #169, #176. Held by: `core/test/message-actions.test.js` "a message carries no action buttons of its own: every action is in the one menu"; `core/test/message-actions.test.js` "a long press with a finger or a long click with the mouse opens the menu, and moving first cancels it"; `smoke:phoneMessageMenu`. **Adopted, not yet built** for media: long press on a photo offers save, react and reply (#181).
- **Reply in thread is offered only on someone else's message.** Why: a thread is started by answering someone. Source: #169, #176. Held by: `core/test/message-actions.test.js` "your own message's menu shows its time and React, never Reply in thread".
- **React uses the composer's own emoji panel**, with the same recents and search; there is no second picker and no fixed tapback row. Source: #169, #176. Held by: `core/test/message-actions.test.js` "React opens the composer's own emoji panel, and the emoji picked there is the reaction"; `smoke:react`.
- **Reactions float at the bubble's outer top corner with no background**: top right of a received message, top left of a sent one, positioned inside the bubble so adding one moves nothing. Source: #182, #176. Held by: `core/test/message-actions.test.js` "the thread opens over a blur that reduced motion keeps without animation, reactions float, and the old surfaces are gone"; `smoke:react`.
- **Threads are one level deep.** A reply to a reply joins the same thread. Source: #183, #176. Held by: `core/test/message-actions.test.js` "a thread is opened by its first message, one level deep, so a reply to a reply joins the same thread".
- **Only a message the engine records with a thread originator is in a thread.** The adapter reads imsg's `thread_originator_guid` alone; `reply_to_guid` (and the `reply_to_sender` and `reply_to_text` imsg resolves from it) is filled by Messages on ordinary rows with the message before it, so it never marks a reply. Two ordinary messages sent a moment apart carry nothing extra. Why: reading `reply_to_guid` marked every consecutive message as a reply to the one above it. Source: #195. Held by: `core/test/threads.test.js` "only a message the engine records with a thread originator is a reply, never one that reply_to_guid chains to the row before it"; `core/test/threads.test.js` "two ordinary consecutive messages show no thread mark".
- **The conversation draws a thread as iMessage on the iPhone does.** Replies keep their place in time. Above the run of replies that holds a thread's newest reply, the original repeats as a small outlined ghost bubble on its own side, with no fill, and a link under it reading the reply count ("2 Replies"). A reply from the other side carries a thin solid curved line on its outer edge, running up toward the ghost, with a small open circle at its top; a reply on your own side needs none. Tapping a reply, its line, the ghost or the count opens the thread. Never a label naming who a reply answers. Source: #195, replacing #183 and #176's per-message mark. Held by: `core/test/threads.test.js` "a real reply connects to its original: a ghost of the original with its reply count above the replies, and a line on the reply from the other side"; `core/test/conversation-press.test.js` "a received reply carries one thread line and never the original body or a reply-to label, its original not loaded included"; `smoke:reply`.
- **A thread opens as its own conversation over the blurred, dimmed conversation**: only its original and its replies, each under its day and time with the delivery status of your last message in it; the contact header stays, with a close (X) control in place of the way back; the composer's field reads "Reply" and adds no row of its own; a reply sent there lands in the thread. Source: #195, replacing #183 and #176's card and "Replying in thread" indicator. Held by: `core/test/threads.test.js` "the thread view lists exactly the original and its replies, with time separators and delivery, under the contact header with a close control, and the composer reads Reply"; `core/test/message-actions.test.js` "an open thread is its own conversation over the rest, which is blurred and inert, and the composer repeats none of it"; `smoke:reply`.
- **Reactions and threaded replies are sends**, under the sending switch and rate limit, refused cleanly where the engine cannot do them. Source: #138, #146. Held by: `smoke:react`, `smoke:reply`. **Adopted, not yet built:** any emoji is sent and shown as a reaction where the engine allows, replacing the six-tapback limit (#188).
- **People outside iMessage receive their own platform's form of reactions and replies**, and a text-fallback reaction they send shows as a reaction. **Adopted, not yet built:** #184.
- **A chat's name is never a machine identifier**: an unnamed group reads as its people, and an inline object character (U+FFFC) is stripped where text is shown. Source: #80, #81. Held by: `core/test/rules.test.js` "chats order newest first and read well".
- **The app never names the messaging transport** in anything a person reads; the repository may. Source: #56, #58. Held by: `core/test/guards.test.js` "the app never names the messaging transport".
- **Read state is the engine's, never a client's idea**: unread comes from the engine and opening a chat marks it read there; recipient read status shows only from engine evidence; typing is not shown where the engine cannot report it. Source: #57, #60, #72, #150; [read-and-typing.md](read-and-typing.md).
- **Emoji are whole characters**: inserted at the caret, deleted as one, surviving the route to the preview and the notice. Source: #72, #77. Held by: `core/test/rules.test.js` "the emoji picker searches by name, keeps categories, and inserts whole characters".

## Screen, window and system edges
